# How the UI rules are applied in PaidLoop

The rules come from the owner's own file `FRONTEND-UI-UX-RULES.md`, which is not copied into this repo because it comes from another project. This page goes through every section of that file and says what PaidLoop does:
- **Applied** means done as written.
- **Adapted** means the idea is kept and the details changed, with the reason.
- **Skipped** means not done, with the reason.

On 9 Nov 2026 every screen was rebuilt on one shared set of parts, to follow the file section by section (the owner's request: "follow each one command" of the file).

## Checks that run by themselves

| Command | What it checks |
|---|---|
| `npm run check:ui` | Colours by role only. Contrast of 54 colour pairs in both themes, including the mixed colours. Spacing, sizes, corner radius, text size, letter spacing and shadows from tokens only. Motion. The import tiers. The route list both ways. The icon file. Raw buttons and browser tooltips in screens. A written reason on every switched-off lint rule. A phone layout for every grid. One h1. Both languages complete. |
| `npm run lint` | ESLint with jsx-a11y (accessibility, recommended rules as errors), React hook rules, TypeScript |
| `npm run check:bundle` | A size limit, gzipped, for each download |
| `npm run build` | All of the above, plus the type check and the build |
| `npm run walk` | Every screen in Chrome at 5 widths, in light, dark, German, compact and reduced motion: 169 checks with axe (needs the app running) |
| `npm run flows` | The main jobs end to end in Chrome: 24 checks (changes the data, so CI runs it on fresh demo data) |

## Owner's choices on 9 Nov 2026

| Question | Answer |
|---|---|
| Font | Inter, served by the app itself (`@fontsource-variable/inter`, OFL licence) |
| Icons | Lucide, as one icon file built from the names in `src/ui/icon-names.ts` (`lucide`, ISC licence, used only by the build script) |
| Accessibility lint | ESLint with jsx-a11y |
| Menu (8 Nov) | Keep the top menu and add room at the sides |

## Section by section

| Section | Status | What PaidLoop does |
|---|---|---|
| **0. Project card** | Applied | **Product:** PaidLoop. **Category:** small business tool with a dashboard. **User:** a small business owner, a few minutes a day, on a laptop or phone. **Slowest device:** a laptop with 2 GB graphics. **Density:** roomy, with a compact option. **Brand colour:** primary blue. **Typeface:** Inter, self-hosted. **Themes:** light and dark. **Languages:** English and German, no right-to-left. **Size limits:** see section 18. |
| **1. Principles** | Applied | Data first. **One look:** one Button, one Badge, one Field, one confirm dialog, one icon set. Fast by default, accessible as the floor, mobile first. Errors and empty states say what to do next. **Looks considered:** a tinted page with white cards, the money figure on a brand surface, icons in soft tinted tiles, and an invoice page that looks like the invoice. |
| **2. Architecture** | Adapted | **Tiers, checked by `check:ui`:** helpers (`api.ts`, `i18n.tsx`) ← `src/ui/` (visual parts, no data) ← `src/widgets/` (business-aware parts) ← `src/pages/` (screens) ← `src/shell/` and the route list ← `App.tsx`. A screen never imports another screen. One file per part, no barrel file. **Navigation is data:** `src/routes.ts` holds each screen's address, page file, template, title and menu entry. The menu, page titles, loading shapes, keyboard keys and the browser walk all read it, and `check:ui` fails if a page file and the list disagree. Each screen is its own download. **Adapted:** React and Vite, not Next.js, so there are no server components, no React Compiler and no route handlers. The design system is a folder, not a package, because there is one app. Screens fetch their own data instead of a separate controller file. |
| **3. The look** | Applied | **Surfaces:** white cards with a 1px hairline on a faintly tinted page, and no shadow on cards. Shadows only on things that float: menus, dialogs, the menu drawer, toasts and the save bar. Buttons and fields have the small contact shadow. No glass and no `backdrop-filter`. **Radius:** 6, pills 4, alerts 8, dialogs 12, inner 3, and round only for dots, step marks and the spinner. **Browser defaults are styled:** thin scrollbars, checkbox colour, the date picker mark, and the app's own labelled search-clear button. One primary colour. **Menu:** a top bar, as the owner chose. It has icons and a clear current page, and below 1280px it becomes a Menu button with a drawer. |
| **4. Colour** | Applied | Primary and neutral 50–900, and success, warning and error at 100/500/700, plus white. The rules file says "23" but its own list adds up to 29. **One change:** warning 700 is one step darker (`#975f00`), so warning text passes 4.5:1 on the tinted page. Screens name roles, never shades. **Mixes:** the page tint, header band, brand surface, status borders, dark-mode status grounds and the dark-mode risk bar are mixes of the palette, and the check measures them like the browser does. **Contrast:** 54 pairs in both themes, read from the real stylesheet: text at 4.5:1, and focus ring, bars and switch at 3:1. **Status colours carry meaning only:** the demo strip is neutral, and people in the audit trail (owner, AI, rules, customer, PayPal) are neutral or blue badges with icons, never green or amber. Dark theme: the same colours with roles swapped. **Skipped:** brand presets for tenants (one owner). |
| **5. Typography** | Applied | Inter Variable is served by the app (Latin and Latin Extended files only, loaded when a page uses them), with Arial stretched to Inter's measurements as the fallback, so nothing moves when it loads. Sizes, weights, line heights and letter spacing come from tokens. Labels are medium weight. Quiet capital labels for sections. Density never changes a font size. The page title is 18px on phones and 20px from 640px. Money uses a real minus sign. **Adapted:** even-width digits on every number and date cell, but not on text cells, because in Inter they also widen the dash and split invoice numbers like RE-2026-0004. |
| **6. Spacing and size** | Applied | Named steps (`--space-hair` to `--space-page`) in two densities. Every size (icons, columns, panel widths, chat height) is a token too. **Checked:** no pixel or rem value in spacing or sizes outside tokens, and no margins except 0 and auto, because blocks are spaced by their parent's gap. One `FieldGrid` part for every form. Every grid has a phone layout, checked on every rule outside an `@media` block. Density switch (Comfortable or Compact) in the View menu, kept on this computer and applied before the first paint. **Adapted:** the comfortable steps are roomier than the ERP values (section 24): 16px page sides on a phone, 24 from 640px, 32 from 1024px, card padding 20 and 24. Controls are 36px from 1024px instead of 34. **Page width (owner, 9 Nov):** every page uses the whole window. Only the side margins stay, and a limit of 1920px stops very large monitors from stretching a page. |
| **7. Layers** | Applied | Five tokens, nothing above a toast. The top bar sits on the navigation layer, so the floating save bar can no longer slide over it (a bug found on 9 Nov). A literal `z-index` fails the check. |
| **8. Motion** | Applied | Speeds and two curves come from tokens. Only opacity and transform are animated (checked). One way in and one way out, the exit one step faster: dialogs fade and rise, the menu drawer slides from the left, menus fade and zoom, toasts slide from the bottom right, tooltips fade in. Nothing moves in forms, lists or sorting. On the bars, hovering one dims the others by opacity (analytics rule). With reduced motion, everything runs once in 1ms and the spinner rests. **Skipped:** the changed-row highlight, because lists are read when opened, not live. |
| **9. Loading** | Applied | Each screen's download and data wait behind one loading boundary, which shows the page title and a skeleton in the template's shape (from the route list). It holds its room at once and draws only after 250ms, and a screen reader hears "Loading" straight away. A panel inside a page that has arrived (Connections) gets its own card skeleton. A button is busy and disabled at once, and the spinner takes its icon's place with words like "Saving...". A re-read keeps the content, dims it, and draws a thin line on the top edge. **Skipped:** dimming the page on a link press (navigation is instant) and percent progress (no long jobs of known size). |
| **10. Page templates** | Applied | Each route names its template (dashboard, list, detail, wizard, settings, customer, catalogue), and the `Page` part sets width and rhythm. One page header: the only h1, actions on its row, a back link under a list, and help behind an (i). **List:** one toolbar with filter tabs and counts, search with a clear button, and on phones a sort choice. The customer name leads in bold and the number is quiet. Tables turn into card lists on phones. **Detail:** the invoice page leads with the invoice itself, like paper. **Form:** required answers lead with stronger labels. Help shows only while a field has focus, or with its error. Every refusal points to its fix ("Fix this", "Open settings"). **Settings:** each card saves itself (business, agent limits, PayPal, local AI). **Wizard:** a stepper on top. **Dashboard:** figures across the top. **Wide screens (owner, 9 Nov):** from 1280px the invoice page, Approvals and the check step show a main column and a side column, and Settings shows its cards two by two with their Save buttons lined up. The customer page shows payment and chat side by side from 1024px. **Adapted:** the rules file's ERP default is one column, but the owner asked that every page use the whole width. Filters are tabs with counts instead of a "Filter ▾" menu, because the counts are useful. Dashboard panels sit in two columns from 1024px. A required field gets a stronger label but not a taller box, so rows stay aligned. **Skipped:** right-click row menus (hard to find), focus mode, and a leave-page warning (the unfinished invoice is kept instead). |
| **11. Navigation and shell** | Adapted | A sticky top bar with a hairline holds the wordmark, the menu with icons, PayPal and AI status, language, and a View menu (theme, spacing, keyboard shortcuts). Exactly one link is current, and an invoice keeps "Invoices" current. Below 1280px the menu, language and view settings move into a drawer from the left, which keeps focus inside, closes with Escape and gives focus back (checked by `npm run flows`). **Skipped:** sidebar (the owner chose the top menu), command palette, pinned screens, preferences saved on a server, and permissions or tenants. |
| **12. Components** | Applied | Built once in `src/ui/`: Split and CardGrid (the wide-screen layouts), Icon and IconTile, Button and ButtonLink, Badge, Field, FieldGrid, Switch, Checkbox, SearchField, FilterTabs, Segmented, SectionCard, StatTile, EmptyState, Alert, ConfirmDialog, Dialog, Drawer, PopoverButton, Tooltip, PageHeader, Page, Stepper, BarRows, Loading, Toast. **ConfirmDialog is the only confirm** (the old two-click button is gone). Pills always carry words. Toasts appear bottom right only. **Design catalogue** at `#/design` (not in the menu): every colour role, text size and part in its states, walked with axe at every width and in both themes. **Icons:** 70 Lucide icons in one file, one cached download, line colour from the text. `check:ui` fails if a listed name has no drawing. Native date inputs are kept. **Adapted:** one icon set serves both roles; the two-tone look comes from the tinted icon tile instead of a separate duotone set. |
| **13. Data and live UX** | Adapted | Not a realtime app: the browser asks the server, and the server asks PayPal every 20 seconds. **Applied:** server search is prefix search with an index range (checked by a test), and the audit list uses cursor paging. **Adapted:** the invoice list uses page numbers, because it can be sorted by any column and is not live. |
| **14. Responsive** | Applied | Mobile first. Verified at 320, 375, 768, 1024 and 1440 by the walk, with no sideways scroll and nothing past the right edge. Every touch target is at least 40px on a phone (checked). The main area is a flex column. |
| **15. Accessibility** | Applied | ESLint with jsx-a11y, recommended rules as errors, and every rule switched off at one place carries a written reason (checked). axe runs on every screen, at every width, in both themes, German, compact and reduced motion. Visible text is always part of a button's name (WCAG 2.5.3, fixed on 9 Nov for the status button and the language switch). Skip link, visible focus ring, labelled fields, errors tied to fields, one h1, headings in order, colour never alone. Dialogs and the menu drawer use the native `<dialog>`, so focus is trapped and given back. **Not tested:** a real screen reader. |
| **16. Keyboard** | Adapted | Not a data-entry product, so there are no Tally-style keys. N, I, A and H go to a screen (read from the route list), `/` jumps to search, `?` lists the shortcuts, and Ctrl+Enter does the main action of a step. Escape closes menus and dialogs and clears the search. Letter keys do nothing while typing. |
| **17. Brand and logo** | Applied | The whole word is the logo, in one colour (the brand role, so it works in dark mode). The app icon is a P drawn as one loop (`public/favicon.svg`), and the browser bar gets a theme colour in light and dark. The PDF invoice carries the owner's business, never the product logo. **Not done:** PNG app icons for phones' home screens. |
| **18. Performance** | Applied | Size limits per download, gzipped, checked in every build. **Measured on 9 Nov:** entry 70.3 KB of 75 (React alone is about 45). Stylesheet 10.3 of 16. New invoice 6.8 of 12. Every other screen under 4 of 12. The customer page 2.2 of 8: a customer never downloads the owner's screens. Icons 3.5 of 8. Fonts load only when a page uses their letters. No `backdrop-filter`, and only loaders animate on repeat. No service worker. |
| **19. Print** | Applied | Printing the invoice page prints only the invoice itself, without menus or buttons. The official print is the PDF in the customer's language. |
| **20. Content and microcopy** | Adapted | Sentence case. One date format per language: "9 Nov 2026" and "9 Nov 2026, 23:50" in English, "09.11.2026" in German (fixed on 9 Nov; times used another format). One money format per language, with a real minus sign. Errors say what happened and the fix, and empty states carry their action (Approvals now offers "Run follow-up agent"). **Adapted:** error text is chosen by the server in the requested language, not from a code map in the browser. |
| **21. Don'ts** | Applied | Each one is a check in `check:ui`, `lint` or `check:bundle`, or true by construction. |
| **22. Enforcement** | Applied | See the table of checks above. The exemption list for older files (`LEGACY` in `check-ui-rules.mjs`) exists for the ratchet and is empty. |
| **23. Testing the UI** | Adapted | The walk drives Chrome over its debugging port, so there is no Playwright install. It reads every screen from the route list, adds four more states (details step, filtered list, paid invoice, Settings > Connections), and checks 169 screens. `FULL=1 SHOTS=folder` saves whole-page screenshots for a human look. `npm run flows` uses the screens like an owner (24 checks), and CI runs it after the walk. **Not done:** a signed-in walk as two roles (there is one role). |
| **24. Category** | Applied | Treated as a small business tool plus a dashboard. Tokens, templates, accessibility and the loading rules are kept. Presets and the command palette are skipped. Not dense, so only the spacing values changed, not the mechanism. |
| **25. Starter prompt** | Not needed | The app already existed. |
| **26. Definition of done** | Applied | **Templates:** from the route list. **Spacing, colour and motion:** `check:ui`. **Widths, themes, density, reduced motion and axe:** the walk. **Keyboard:** the flows and the walk. **Loading:** the skeleton rules above. **Empty, error and fix-link states:** in every screen. **Size:** `check:bundle`. **Looks considered:** judged by a person on the screenshots. **Docs:** this page. |
| **27. Process** | Applied | The plan was approved by the owner before the work. Decisions are written here and in `docs/USABILITY.md`. |

## What a new screen must do

1. Add it to `src/routes.ts` with its template, then build it from the parts in `src/ui/`: `Page`, `PageHeader`, `SectionCard`, `Button`, `Field`, and so on. Show `Loading` with the template's shape while data is missing.
2. Use roles and size tokens from `tokens.css`. Do not write a colour, a size, a margin or a duration in a screen.
3. Give every table `className="rtable"` and `data-label` on every cell, so it becomes cards on a phone.
4. Write every text in both languages in `i18n.tsx`.
5. Run `npm run build`, `npm run walk` and `npm run flows`. All must pass.
